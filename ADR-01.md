# ADR-001: Выбор веб-фреймворка для микросервисов FinGuard

**Дата:** 2026-07-25  
**Статус:** Принято

## Контекст
Для микросервисной платформы FinGuard (приём транзакций, симулятор, фрод-детектор, RAG-ассистент) требуется Python-фреймворк, обеспечивающий:
- высокую пропускную способность (поток транзакций),
- строгую валидацию на входе,
- автоматическую генерацию OpenAPI 3.0,
- нативную асинхронность (Kafka, Redis, gRPC),
- минимальный оверхед для контейнеризации.

## Альтернативы
- **FastAPI** (Starlette + Pydantic)
- **Flask** + Flasgger + Marshmallow
- **Django REST Framework** (DRF)

## Сравнение
| Критерий | FastAPI | Flask + расширения | DRF |
|----------|---------|-------------------|-----|
| Производительность | Высокая (ASGI, uvloop) | Средняя (WSGI) | Средняя (WSGI) |
| Валидация | Pydantic (встроена) | Marshmallow (вручную) | Сериализаторы DRF |
| OpenAPI | Автоматически | Плагины (flasgger) | Автоматически |
| Асинхронность | async/await из коробки | Через Quart | Частичная |
| Связь с ORM | Отсутствует | Отсутствует | Жёсткая (Django ORM) |
| Кривая обучения | Низкая | Низкая | Средняя |

## Решение
Выбран **FastAPI** на основании:
1. **API-First:** единый источник правды — Pydantic-модели, Swagger UI без дополнительных инструментов.
2. **Асинхронность:** неблокирующая работа с Redis (idempotency store) и Kafka (publisher) повышает пропускную способность.
3. **Безопасность:** строгая валидация отсекает некорректные данные до бизнес-логики.
4. **Микросервисная архитектура:** отсутствие ORM упрощает использование специализированных клиентов (aiokafka, redis-py).

## Последствия
- Разработчики должны знать async/await и избегать синхронных вызовов.
- Для сложных CRUD‑сценариев может потребоваться больше кода, чем в DRF, но в FinGuard таких сценариев нет.
- Необходим асинхронный HTTP‑клиент (httpx) для внутренних вызовов.
